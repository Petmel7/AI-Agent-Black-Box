# AI Agent Black Box v0.1 — Evidence Recorder

**Status:** Approved

**Date:** 2026-09-21

## Product Statement

AI Agent Black Box v0.1 records a Codex coding run and produces a reviewable evidence page that answers:

- What was the agent asked to do?
- What observable actions did it take?
- What changed in Git?
- What commands and tests ran, and with what results?
- Which deterministic risks are present?
- Which summary claims are supported by evidence?

The v0.1 outcome is an evidence recorder, not an autonomous merge gate and not a general-purpose LLM observability platform.

## Target User

The initial user is a single developer running Codex against a local Git repository and reviewing the result in a private dashboard.

## Core User Journey

1. The developer starts a Codex task through the Black Box collector.
2. The collector records the repository baseline, including the base commit and pre-existing working-tree changes.
3. Codex emits available telemetry and performs observable tool and command actions.
4. The collector records the final Git state and uploads normalized evidence in retryable batches.
5. The backend persists immutable evidence, creates queryable projections, and runs deterministic analysis.
6. The backend generates a summary whose important claims link to evidence.
7. The developer opens the run page and inspects metrics, timeline, diff, tests, findings, and summary.

## In Scope

### Codex adapter

- One supported agent: Codex.
- Capture supported Codex telemetry through documented OTel or hook integration.
- Associate telemetry with a Black Box run identifier.
- Record model and token metadata when the source provides it.
- Treat cost as unavailable or estimated unless the provider reports an authoritative value.

### Local collector

- A cross-platform Node.js CLI invoked around a Codex run.
- Capture the Git base commit and pre-run dirty state.
- Capture the post-run Git state.
- Distinguish pre-existing changes from changes observed during the run where the available evidence allows it.
- Redact configured secret patterns before upload.
- Batch events and artifacts.
- Use a local SQLite spool for retry after network or server failure.
- Never discard an undelivered run silently.

### Ingestion

- Machine-facing HTTP API.
- API-token authentication for the single v0.1 workspace.
- Versioned, runtime-validated event batches.
- Idempotent batch and event ingestion.
- Separate storage for large artifacts.
- Queue analysis asynchronously and return without waiting for analysis.

### Evidence model

- Run start and completion.
- Observable tool calls and results exposed by the adapter.
- Commands, exit codes, duration, and bounded output excerpts.
- File changes and Git diff metadata.
- Test commands and their observable outcomes.
- Errors and failed attempts.
- Token counts and duration when available.
- Content hashes and evidence references.

### Deterministic findings

The first rules should cover at least:

- Sensitive-area changes: authentication, authorization, payments, infrastructure, migrations, secrets, and dependency manifests.
- Production changes without related test changes or observed relevant tests.
- Tests not run after the last relevant code change.
- A final working-tree state different from the state on which the last successful tests ran.
- Repeated failed commands.
- Lockfile changes without a corresponding manifest change.
- Test removal or weakening detectable from the diff.
- Files changed outside the declared task scope when scope evidence is available.
- An agent success claim without matching observable test evidence.

Rules must return severity, stable rule identifier, explanation, and evidence references. A rule may return `unknown` rather than inventing evidence.

### Evidence-backed summary

- Generate the summary only after deterministic analysis.
- Separate observed facts from inference.
- Link material claims to events, file changes, tests, or findings.
- Mark unsupported or incomplete conclusions explicitly.
- Do not store hidden chain-of-thought.

### Dashboard

- Run list with status, repository, duration, files changed, tests, findings, and token metadata.
- Run detail page with overview, timeline, changed files, commands, tests, errors, findings, and summary.
- Direct navigation from a finding to its supporting evidence.
- Clear distinction among `PASS`, `REVIEW`, `FAILED`, `INCOMPLETE`, and `PROCESSING` run states. These are v0.1 presentation states, not configurable policy decisions.

### Export

- Export one run as a versioned JSON evidence bundle.
- Include hashes and references but exclude secrets and server credentials.

## Out of Scope

- GitHub App, pull-request comments, and GitHub Checks.
- GitHub CI evidence ingestion.
- Claude Code, Copilot, Cursor, OpenCode, or other agent adapters.
- Team accounts, invitations, RBAC, SSO, or enterprise tenancy management.
- Configurable repository policy files and merge blocking.
- Automatic test generation or execution in remote isolated workers.
- Agent budgets, fleet analytics, model comparison, and team dashboards.
- SIEM integration, compliance exports, and data-residency controls.
- Live terminal streaming to the browser.
- Full replay of an agent's internal reasoning.
- A universal numeric quality score.
- Automatic remediation of findings.

## Product Constraints

- The recorder must not modify the developer's source files except through the wrapped agent itself.
- A telemetry outage must not prevent the agent from finishing its work.
- Evidence capture must fail visibly and preserve recoverable local state.
- Raw prompts and command output are opt-in data. Metadata-first collection is the safe default.
- Findings must prefer `unknown` over false certainty.
- The dashboard must not imply that passing tests prove complete correctness.

## Success Criteria

v0.1 is successful when a developer can complete the core journey on a Git repository and, for one recorded Codex run:

- See the correct base and final Git states.
- See commands, failures, and observed tests in chronological order.
- Distinguish pre-existing changes from run-attributed changes or see an explicit uncertainty state.
- Inspect at least the initial deterministic findings with evidence links.
- Read a summary that cites stored evidence rather than unsupported claims.
- Restart after a simulated upload failure and deliver the locally spooled run without duplicates.
- Export the run as a versioned JSON bundle.

## Non-Goals for Initial Architecture

- Optimizing for millions of runs before the canonical schema is proven.
- Splitting the product into independently owned microservices.
- Hiding provider differences behind a lowest-common-denominator schema.
- Making Supabase-specific behavior part of the core domain model.
