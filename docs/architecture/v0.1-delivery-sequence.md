# v0.1 Delivery Sequence

**Status:** Accepted for v0.1

**Last updated:** 2026-09-22

## Purpose

This document orders the remaining v0.1 work by architectural dependency. It is
not a release promise and does not replace approved task specifications. A later
task may be split when implementation risk or review size requires it, but work
must not bypass the dependency that makes its evidence trustworthy.

## Completed Foundation

1. **BBX-001 — Bootstrap monorepo.** Established the modular-monolith process
   boundaries, shared tooling, and CI.
2. **BBX-001A — Update GitHub Actions runtimes.** Pinned the supported runner and
   Node 24 action runtimes.
3. **BBX-002 — Canonical Evidence Contracts.** Established the strict version 1
   evidence envelope, event kinds, artifact references, and batch invariants.

## Remaining Dependency Order

### BBX-003 — Evidence Persistence Foundation

Create the first PostgreSQL schema, migration, and database integration-test
boundary for organizations, repositories, runs, accepted batches, immutable raw
events, batch membership, and declared artifact metadata.

This comes first because every later write path depends on durable tenant,
identity, ordering, and append-only constraints.

### BBX-004 — Idempotent Ingestion Write Path

Implement the authenticated, versioned batch endpoint and one transactionally
safe application service that validates a batch, resolves exact retries versus
conflicting identifier reuse, persists new records, and records durable
processing intent before returning success.

This task must make a separate architecture decision for the processing-intent
and queue handoff guarantee before implementation.

### BBX-005 — Artifact Transport and Storage

Add authorized artifact upload coordination, post-redaction byte/hash
verification, object storage, and retry-safe metadata finalization. Keep storage
locations server-owned and outside canonical client events.

### BBX-006 — Local Collector Core

Implement local run identity, monotonic sequence allocation, bounded capture,
redaction, batching, SQLite spooling, retry, and visible recovery state. Prove
that backend failure does not prevent the wrapped process from completing and
does not silently discard evidence.

### BBX-007 — Git Evidence Capture

Capture the base commit, pre-existing dirty state, checkpoints, final state, and
post-redaction status/diff artifacts. Preserve explicit uncertainty when a
change cannot be attributed confidently to the run.

### BBX-008 — Codex Adapter and Wrapped Run

Integrate only documented Codex telemetry or hooks, map provider observations to
the canonical contract, correlate them with collector-owned run identity, and
close the first local end-to-end recording path.

### BBX-009 — Processing and Query Projections

Consume durable processing work, build replayable run/command/test/file/error
projections, and expose explicit processing states without mutating raw
evidence.

### BBX-010 — Deterministic Findings

Implement the initial versioned rule catalog, evidence references, `unknown`
outcomes, and reprocessing semantics.

### BBX-011 — Evidence-backed Summary

Generate summaries only after deterministic analysis. Separate observations
from inference and require evidence references for material claims.

### BBX-012 — Evidence Dashboard

Implement the run list and the first killer run-detail screen using projections,
with navigation from findings and summary claims to raw evidence.

### BBX-013 — Export and v0.1 End-to-End Hardening

Export a versioned JSON evidence bundle and prove the complete journey,
including restart after upload failure, duplicate-free delivery, processing,
review, and export.

## Sequencing Rules

- Do not build ingestion persistence before BBX-003 constraints are accepted and
  tested.
- Do not build collector retries before the server's duplicate/conflict contract
  is defined.
- Do not build projections, findings, summaries, or dashboard views directly on
  provider-native payloads.
- Do not generate summaries before deterministic findings and evidence-reference
  validation exist.
- Do not add GitHub App, pull-request, multi-agent, configurable policy, automatic
  QA, fleet, or enterprise behavior during v0.1.
- Prefer one end-to-end slice over parallel partial implementations when a later
  task reveals that this ordering needs refinement.

## Decision Gates

- BBX-003 requires acceptance of ADR-0003.
- BBX-004 requires a decision for atomic processing intent and queue handoff.
- BBX-005 requires an artifact upload and server-side integrity protocol.
- BBX-006 requires a local spool state-machine and redaction threat model.
- BBX-008 requires a documented Codex integration surface; unsupported provider
  behavior must remain explicitly unavailable.
