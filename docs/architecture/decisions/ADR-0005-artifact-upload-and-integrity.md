# ADR-0005: Authorized Artifact Upload and Server-Verified Integrity

- **Status:** Accepted
- **Date:** 2026-09-24
- **Decision owners:** Project architecture

## Context

Canonical events declare artifact identity and integrity metadata but cannot
contain storage locations or verification claims. Large diffs, logs, and reports
must reach private object storage without passing their request bodies through
the ingestion service, exposing storage credentials, permitting object-key
selection, or trusting a collector's claim that uploaded bytes match the
declaration.

The protocol must tolerate interrupted and repeated delivery. A declaration may
exist before its bytes, and failed transport must not mutate append-only raw
evidence. Supabase Storage is the v0.1 infrastructure choice, while the domain
state and integrity rules must remain portable to another S3-compatible store.

## Decision

Use a two-phase, capability-authorized upload followed by server-side integrity
verification.

### Declaration precedes transport

An artifact can be uploaded only after its immutable canonical declaration was
accepted through the evidence-batch endpoint. The ingestion service resolves
the declaration under the authenticated organization and repository. It never
accepts organization identity, bucket, object key, or storage URL from the
collector.

The declared `byteLength` and `sha256` describe the exact byte sequence sent to
storage after local redaction and any declared compression. The server does not
infer that redaction was sufficient; it verifies only that stored bytes match
the accepted declaration.

### Direct resumable upload

For v0.1, the ingestion service issues a short-lived signed capability for a
direct TUS resumable upload to a private Supabase Storage bucket. The response
uses a versioned, runtime-validated Black Box contract and identifies the
protocol, upload attempt, endpoint, required capability token, expiry, and
transport limits. Provider credentials are never returned.

The object key is generated by the server from opaque server-owned identity. It
is not supplied by the collector, used as canonical evidence identity, or
stored in raw evidence. Uploads never use overwrite/upsert behavior. Every new
attempt receives a fresh object key so an interrupted, expired, rejected, or
malicious attempt cannot replace another object's bytes.

The signed capability is scoped to one object and treated as a secret. It must
not be persisted in PostgreSQL or emitted to logs, errors, traces, or evidence.

### Completion and verification

After storage reports upload completion to the collector, the collector calls
the authenticated completion endpoint with only canonical and server-issued
identifiers. It cannot provide a storage URL, object key, observed hash, or a
trusted completion result.

The server opens the server-owned object through an injected storage port,
streams it through SHA-256 calculation, counts the bytes, and enforces the
configured maximum without buffering the complete artifact. Neither an ETag,
client checksum, provider metadata, nor a successful upload response is proof
of integrity.

For the bounded v0.1 artifact size, completion performs this verification in
the machine-facing service before returning `verified`. The operation is
idempotent and protected by a bounded database lease: concurrent or repeated
completion may repeat safe reads but cannot create multiple verified objects or
publish conflicting state. A future asynchronous verifier may reuse the same
state machine without changing canonical evidence.

### Durable operational state

Artifact declarations remain append-only. Storage attempts are separate,
mutable operational records containing trusted organization, run, declaration,
server-owned object key, attempt state, lease and expiry timestamps, and
observed verification results.

The closed attempt states are:

- `issued`: an upload capability has been issued;
- `verifying`: one verifier currently owns a bounded lease;
- `verified`: observed byte length and SHA-256 match the declaration;
- `rejected`: the object is missing, exceeds the limit, or fails integrity;
- `expired`: the capability elapsed before successful verification.

Database constraints enforce ownership, unique object keys, monotonic legal
state transitions, and at most one verified attempt per artifact declaration.
No storage state rewrites the canonical declaration.

An upload-session request is idempotent by artifact declaration: it returns the
same unexpired usable attempt when safe, reports the existing verified result,
or creates a fresh attempt after expiry or rejection. Completion of a verified
attempt returns the original verified result. Integrity failure records only
safe observed metadata and a stable error code, rejects that attempt, and
allows a later fresh attempt.

Deletion of rejected or abandoned objects is best-effort and never turns a
failed verification into success. Durable stale-attempt cleanup and retention
automation may be added later; private, unverified objects are never exposed to
dashboard or export consumers.

### Security and portability

- The bucket is private; public object URLs are forbidden.
- Download capabilities are separately authorized and time-limited; public
  download behavior is outside BBX-005.
- Only server infrastructure knows the bucket, object key, and service
  credential. Completion never dereferences a client URL, preventing an SSRF
  path.
- Provider-specific SDK types and TUS details stay in the storage adapter and
  upload HTTP contract. Domain services depend on a small storage port.
- Tests use a deterministic in-memory adapter and do not require network access
  or real Supabase credentials. Optional provider contract testing is separate
  from the deterministic repository gate.

## Initial Limits

The default maximum artifact payload is 50,000,000 bytes. The server rejects a
declaration above the configured limit before issuing a capability and rejects
an observed stream that crosses the limit. The value is explicit configuration,
reported in the upload contract, and may be lowered by deployment. Raising it
requires validating service timeouts and storage limits; it does not change the
canonical evidence schema.

## Consequences

### Positive

- Large bytes bypass the Node.js request body while authentication and object
  naming remain server-controlled.
- TUS gives the later local collector resumable transfer on unstable networks.
- Verification is based on stored bytes rather than client or provider claims.
- Retry and concurrency failures cannot overwrite raw declarations or verified
  objects.
- Storage-provider details remain outside canonical evidence and domain state.

### Negative

- Completion performs one bounded read of every uploaded object and can take
  longer than ordinary ingestion requests.
- Upload attempts and verification leases add operational state and cleanup
  needs.
- The initial transport adapter uses a Supabase TUS capability even though the
  integrity model is provider-neutral.
- The 50,000,000-byte v0.1 bound requires collectors to omit, truncate, or split
  larger logical output under a later collector policy.

## Alternatives Considered

### Proxy artifact bytes through Fastify

Rejected because it places large and resumable request bodies on the ingestion
process and duplicates object-storage transport responsibilities.

### Trust an upload response, ETag, or client checksum

Rejected because these values do not independently prove that the private
object matches the accepted canonical declaration.

### Presigned single PUT only

Rejected for v0.1 because interrupted large uploads would restart from zero.
The protocol contract can gain another closed transport variant later without
changing artifact identity or verification semantics.

### Content-address one object across declarations

Rejected for v0.1 because cross-run or cross-tenant deduplication complicates
authorization, deletion, and provenance. Hashes prove integrity; they do not
grant object identity or access.

### Asynchronous verification in BBX-005

Deferred. It would require an additional durable relay/consumer path before
BBX-009. Bounded synchronous verification supplies a complete first slice while
preserving a state machine that can move to the worker later.

## Follow-up Work

- BBX-005 implements the upload, attempt, storage-adapter, and verification
  boundaries.
- BBX-006 stores resumable upload state in the collector spool and never loses
  an unverified artifact silently.
- BBX-009 may move verification execution behind durable background work and
  makes missing/unverified artifacts visible to processing projections.
- Dashboard/export tasks authorize access only to verified objects.
- A later lifecycle decision defines automated orphan cleanup and retention.
